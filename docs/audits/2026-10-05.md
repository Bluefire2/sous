# Audit — Sous

2026-10-05. Written at the repo root as `AUDIT-2026-10-05.md` because
`AUDIT.md` (2026-08-30) already existed and describes an earlier version of
the app. Both now live in `docs/audits/`; the older one is
[2026-08-30.md](2026-08-30.md). Line numbers below are as of 2026-10-05.

Scope: `scripts/server.ts`, every route module under `server/` that the
dispatcher mounts (auth, membership, session, sync, photos, stt, translate,
agent route, import route, extension import, public links, MCP route, OAuth
authorize/token/store, client metadata), the store's recipe and push
validation paths, the client fetch layer (`src/lib/remote.ts`,
`syncEngine.ts`, `session.ts`), `App.tsx`/`main.tsx`, `vite.config.ts`, the
Chrome extension, the Dockerfile, `scripts/deploy.sh`, both GitHub workflows,
`README.md`, `AGENTS.md`, `.env.example`, and the legal pages' coverage of
newer features. Large transaction-heavy modules (`server/grants.ts`,
`sharedPull.ts`, `store.ts` cascades, `src/lib/libraryMemory.ts`,
`recipeStore.ts`) were read selectively and otherwise relied on their tests.

What ran. The worktree's `node_modules` was stale (the MCP SDK and Playwright
were missing), so the first `npm run build` and `npm test` failed on import
resolution; that was the environment, not the code. After `npm ci`:
`npm run build` is clean (`tsc -b` and Vite), and `npm test` passes 2474 tests
in 141 files. `npm audit --omit=dev` reports 3 advisories (see Low 7). Two
findings below were reproduced by running the API-only listener locally with
a signed session cookie and no Gemini key; the script is described in each
finding. Not run: the Firestore emulator, test mode, any Gemini call, the
Chrome extension, Playwright, anything against Cloud Run.

## Overall assessment

Sous is a Vite SPA plus a hand-written Node server over Firestore, Cloud
Storage and Gemini, with its own invite-only membership tier, collection
sharing, public read-only links, and a remote MCP server with its own OAuth
2.1 authorization server. For a personal project it is unusually
disciplined. Every protected route runs the same `requireMember` decision and
keeps the documented 401/503 split; HMAC-signed hop cookies each carry their
own `v` family so one never verifies as another; the MCP token store hashes
every secret, rotates refresh tokens with a reuse grace window, and revokes a
grant on code or token replay; the public-link reads recheck the whole chain
on every request; server-rendered pages escape every interpolated value; and
`scripts/invariants.test.ts` turns many of the rules in `AGENTS.md` into
failing tests. The documentation in `AGENTS.md` matched the code everywhere
I checked it, including the cookie families, the header-auth exception, the
import log contents, and the account-deletion steps.

The problems are at the edges, and they are mostly inconsistencies between
newer and older code rather than design faults. The newest module, the MCP
client-metadata fetch, is a careful SSRF-safe pinned fetch; the oldest
network call, the URL import fetcher, still has the scheme-only check that
the August audit scoped out, and no response cap. The chat handler, the one
route that still lives in `api/` for Vercel's sake, is also the one route
without body validation, a size cap, or a key check, and it is the only one
whose errors reach the dispatcher's `console.error`. The README has
accumulated two duplicated sections and some stale version facts, and the
old `AUDIT.md` at the root describes an app that no longer exists. None of
this argues for structural change.

The second half of the brief was low-hanging features. Those are in their
own section after the findings, each anchored to the code that makes them
cheap, and one obvious candidate (copying a shared recipe into your own
library) is listed as deliberately ruled out by the sharing plan.

## Medium

### 1. The URL import fetcher reaches loopback and private addresses, follows redirects unchecked, and buffers the whole response

[server/recipeImport.ts:359](../../server/recipeImport.ts:359),
[server/recipeImport.ts:372](../../server/recipeImport.ts:372),
[server/recipeImport.ts:380](../../server/recipeImport.ts:380) — CONFIRMED

`fetchPageHtml` validates only the scheme; its own comment says it "does not
block private or link-local destinations". It passes `redirect: 'follow'`,
so even a public hostname can redirect to an internal one, and it ends with
`await page.text()` with no byte cap and no timeout. The extension path caps
HTML at 600 000 characters ([server/extensionImport.ts:31](../../server/extensionImport.ts:31))
and the import body at 12 MB, but the URL path has no equivalent for the
fetched page.

Reproduced: with the API-only listener on port 3999 and a tiny HTTP server
on `127.0.0.1:3998` that logs each hit, a signed-in member's
`POST /api/import {"url":"http://127.0.0.1:3998/internal"}` produced
`TARGET HIT: GET /internal ua=Mozilla/5.0 (iPhone; ...` on the target and a
502 `import-model-failed` from Sous (no Gemini key). The server fetched an
internal address on the member's behalf and would have handed the page to
Gemini.

Impact is bounded: the route is members-only, Sous is invitation-only, Cloud
Run's metadata server refuses requests without the `Metadata-Flavor` header,
and the response is only ever turned into a recipe draft. What remains is
internal probing from the service's egress identity and a memory exhaustion
path: a member pointing the import at a multi-gigabyte URL makes a 512 MiB
container buffer it. This gap is recorded as out of scope in
[docs/plans/audit-fixes.md:750](../../docs/plans/audit-fixes.md:750), so it is a
known decision, but the MCP work has since built exactly the tools to close
it: `isPublicAddress` ([server/mcp/oauth/clientId.ts:162](../../server/mcp/oauth/clientId.ts:162))
and the DNS-pinned, size- and time-capped fetch in
[server/mcp/oauth/clientMetadata.ts:144](../../server/mcp/oauth/clientMetadata.ts:144).

Fix (a few hours): resolve the hostname with `dns.lookup({ all: true })`,
refuse unless every address passes `isPublicAddress`, pin the connection to
the checked address (the `lookup` option, as `clientMetadata.ts` does), use
`redirect: 'manual'` and re-run the check on each `Location`, add
`AbortSignal.timeout`, and read the body through a capped reader (the one in
`server/photos.ts` `readCappedBytes` is reusable) at the same 600 000
characters the extension uses. `fetchPageHtml` already takes an injectable
`fetchImpl` and has a test block at
[server/recipeImport.test.ts:801](../../server/recipeImport.test.ts:801), so the
address check can be tested without the network by injecting a resolver.
Keep `/privacy` unchanged; it already says the server fetches the page.

### 2. `/api/chat` has no body validation, no size cap, and no API-key check, and its errors escape to the dispatcher

[api/chat.ts:259](../../api/chat.ts:259), [api/chat.ts:260](../../api/chat.ts:260),
[api/chat.ts:263](../../api/chat.ts:263),
[scripts/server.ts:278](../../scripts/server.ts:278) — CONFIRMED

Every other model route reads its body through `readBoundedText`
([server/membership.ts:233](../../server/membership.ts:233)), checks the shape,
and returns 503 when `GEMINI_API_KEY` is unset (`server/stt.ts:186`,
`server/agent/route.ts:66`). The chat handler does `await req.json()` with a
type cast, constructs the Gemini client with whatever the key is, and awaits
`generateContentStream` with no try/catch. Anything that throws before the
stream is returned propagates to `handleRequest`, which logs the raw error
and answers a `text/plain` 500.

Reproduced with a signed session and no key:

```
chat <- "not json": 500 "Internal error"     (log: SyntaxError: Unexpected token 'o', "not json" is not valid JSON)
chat <- {}:         500 "Internal error"     (log: TypeError: Cannot read properties of undefined (reading 'map'))
import <- "not json": 400 {"error":"Bad request","code":"bad-request"}
```

Failure scenarios: a client bug or an old cached client sends a malformed
body and the user sees "Assistant request failed (500)"
([src/lib/chatApi.ts:68](../../src/lib/chatApi.ts:68)) with nothing to act on; a
deploy without `GEMINI_API_KEY` fails the same way instead of the 503 the
other routes give; `messages[].images` has no count or size limit, so one
chat turn can carry an arbitrarily large base64 payload to Gemini; and a
Gemini SDK error at `generateContentStream` is logged verbatim by the
dispatcher. `AGENTS.md` treats that last case as a privacy risk for import
("an SDK message can quote the request") and wraps import in
`sanitizedImportError`; chat's request includes the whole recipe JSON in the
system instruction and gets no such wrapper. Whether a given SDK message
actually echoes the prompt I could not verify without a live key, so treat
the log-leak part as PLAUSIBLE and the 500s as CONFIRMED.

Fix (1 to 2 hours): the file cannot import siblings (Vercel), so inline a
bounded read and a shape check (`messages` is a non-empty array of
`{ role, content, images? }` with `images` capped like
`server/importRoute.ts` caps them), return 400/413 on failure, return 503
when the key is blank, and wrap the `generateContentStream` await so a
provider failure becomes a 502 with a fixed message. `api/sessionGate.test.ts`
shows the existing pattern for testing this file without the network.

## Low

### 3. Three member routes buffer the entire body before checking its size

[server/sync.ts:308](../../server/sync.ts:308),
[server/extensionImport.ts:124](../../server/extensionImport.ts:124),
[server/translateRoute.ts:200](../../server/translateRoute.ts:200) — CONFIRMED

`syncPush` and `extensionImport` call `req.text()` and only then compare
`raw.length` to their limits; `translatePost` calls `req.json()` with no
limit at all and relies on `translationExceedsCaps` afterwards. The agent,
import, feedback, MCP and OAuth routes all use `readBoundedText`, which
cancels the stream as soon as the limit is crossed. Cloud Run caps a request
at 32 MB, so the exposure is a member sending 32 MB bodies at a 512 MiB
instance, not an outsider. `raw.length` also counts UTF-16 code units, not
bytes, so the "1 000 000 byte" limit is approximate. Fix (minutes each):
replace the three reads with `readBoundedText(req, LIMIT)` and map `null`
to the existing 413.

### 7. `npm audit` reports three production advisories that CI does not surface

[package-lock.json](../../package-lock.json) — CONFIRMED

`npm audit --omit=dev`: `@grpc/grpc-js 1.14.0–1.14.4` (high; both advisories

nothing in CI would have told you: `dependency-review-action` only runs on
pull requests and only examines dependencies the PR changes. Fix (minutes):
run `npm audit fix`, confirm `npm test` and `npm run build`, commit the lock
file.

## Low-hanging features

Each of these is small because the data or the hook already exists. Any new
user-facing text must land in all four `src/i18n/` catalogs and go through
the in-context review before the PR (`AGENTS.md`, UI text rule); the ones
marked "no new text" avoid that.

### A. Search ingredients, not just title and tags

[src/lib/visibleLibraryRecipes.ts:24](../../src/lib/visibleLibraryRecipes.ts:24)

The library filter matches `recipe.title` and `recipe.tags` only. "What can
I make with leeks" is the most common question a recipe app gets, and every
recipe already carries `ingredientSections[].items[].item`. Extend the
predicate to the ingredient `item` strings (and `note`). Hours, including a
test in `visibleLibraryRecipes.test.ts`; no new text if the placeholder
stays.

### B. Tap a tag to filter

[src/screens/Library.tsx:838](../../src/screens/Library.tsx:838)

Tags render as inert `<span>` chips on every card, and the search already
matches tags. Turning each chip into a button that calls `setQuery(tag)`
([src/screens/Library.tsx:752](../../src/screens/Library.tsx:752)) gives tag
filtering for the cost of an `aria-label` catalog entry. Under an hour.

### C. A sort control

[src/lib/libraryMemory.ts:577](../../src/lib/libraryMemory.ts:577)

Recipes are always `updatedAt` descending, with no user choice. Title A–Z,
newest added (`createdAt`), and last cooked (from the `cookLogs` map, which
is already in the library snapshot) are each one comparator in a selector
(`docs/constitutions/client-state.md` wants it in `librarySelectors.ts`),
plus a small menu beside the search box. Half a day with text in four
languages.

### D. "Last cooked" on library cards

[src/lib/librarySelectors.ts:63](../../src/lib/librarySelectors.ts:63),
[src/lib/relativeTime.ts](../../src/lib/relativeTime.ts)

Cook logs are pulled with the library and `selectCookLog` exists, but the
list screen shows nothing about them. A muted "Cooked 3 weeks ago" line per
card uses `relativeTime.ts` for the wording and pairs naturally with C.
Hours.

### E. `/` focuses the search box

[src/screens/Library.tsx:552](../../src/screens/Library.tsx:552)

The screen already owns a document `keydown` listener for Escape. One more
branch (`event.key === '/'` outside an input) focusing the search input is a
few lines and no text. Minutes.

### F. A print stylesheet for the recipe view

[src/screens/RecipeView.tsx](../../src/screens/RecipeView.tsx), [src/index.css](../../src/index.css)

Nothing in `src/` mentions print. An `@media print` block that hides the
header, the Ask panel, the translate chip and the servings controls, and lets
ingredients and steps flow in one column, gives a usable paper copy with no
JavaScript and no text. Under an hour.

### G. Share a recipe as text

[src/screens/RecipeView.tsx](../../src/screens/RecipeView.tsx)

The app is a phone PWA, yet the only way to get a recipe out is a full
library export. `navigator.share({ title, text })` with the recipe rendered
as plain text (title, servings, ingredients, steps, source link), falling
back to clipboard copy, is a single button and a formatter that
`RecipeBody.tsx` already has most of the pieces for (`formatQuantity`, the
source link). Half a day with text.

### Not proposed: copy a shared recipe into your own library

[docs/plans/shared-recipes.md:44](../../docs/plans/shared-recipes.md:44)

Viewers get no edit, move or cook-log controls on shared recipes, and a
"save a copy" button looks like the obvious gap. The sharing plan rules it
out explicitly ("Do not copy recipes into the viewer's tree. Duplication
forks LWW"). I note it so the next reader does not rediscover it.
